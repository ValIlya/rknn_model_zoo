# MMS-TTS RKNN Debug — Session Setup Guide

Starting point for any future agent working on the MMS-TTS RKNN NPU
`log_duration` bug. Read this before touching anything. It records the
environment, verified facts, the experiment harness, and the current state of
the investigation.

---

## 1. TL;DR of the problem

The RKNN-converted MMS-TTS encoder (`mms_tts_eng_encoder_200.onnx`, targeted at
RK3588) produces a **constant, wrong `log_duration`** on the real NPU, while
both the ONNX fp32 reference ("golden") and the RKNN **simulator** are nearly
correct. The collapse is localized to the `flows.2` duration-predictor spline
chain (`Softplus`/`GatherElements`/`Pow`/`Div`/`Add_37..40` → `Concat_57` →
`Mul_81`). `flows.3`/`flows.4` have the *structurally identical* ops and are
**not** affected → data/value-dependent NPU backend bug, not quantization,
optimization level, or model export.

People-icons of previous evidence are in `FINDINGS.md` (this directory) and the
older `softplus_fix.md` (that one contains an UNVERIFIED `Where`-fix claim — do
not trust it).

## 3. Verified facts (do not re-verify unless something looks off)

- `onnx.load(graph.output)` order is fixed and confirmed:
  `[0]='log_duration' [1,1,200]`, `[1]='input_padding_mask' [1,1,200]`,
  `[2]='prior_means' [..,..,192]`, `[3]='prior_log_variances' [..,..,192]`.
  Both `rknn.inference` and onnxruntime return in this exact order.
- `accuracy_analysis` is an **RKNN method**, not a CLI:
  `rknn.accuracy_analysis(inputs, output_dir, target='rk3588')`. It writes
  `{golden, simulator, runtime}/` per-tensor snapshots (one float per line,
  flattened) plus `error_analysis.txt` and `map_name_to_file.txt`.
- `config()` in this toolkit version accepts `op_target=` (confirmed via
  `inspect.signature`); docstring says `{'111':'cpu', ...}` — i.e. the docs are
  ambiguous about key format. **Key semantics were validated empirically** (see
  SESSION LOG / experiment notes). Keys are ONNX node names, NOT op types.
- `RKNN(verbose=True, verbose_file=...)` is available for build logs.
- `do_quantization=False` + `optimization_level=3` +
  `target_platform='rk3588'` is the baseline used for all analysis runs.
- Suspect node names (exact, confirmed by graph dump):
  - `/duration_predictor/flows.2/Softplus` (single Softplus in flows.2)
  - `/duration_predictor/flows.2/GatherElements`, `GatherElements_1`
    … `GatherElements_6` (7 total)
  - `/duration_predictor/flows.2/Pow`, `/duration_predictor/flows.2/Div_3`
  - `/duration_predictor/flows.2/Add_37`, `Add_38`, `Add_39`, `Add_40`
  - `/duration_predictor/flows.2/Concat_57`, `/duration_predictor/flows.2/Mul_81`

## 5. The experiment harness, step by step

On the Orange Pi (venv active):

```bash
# 1) Run one build+analysis variant. op_target is a JSON dict of node->"cpu".
python /home/ubuntu/rknn_model_zoo/examples/mms_tts/python/harness/aa_variant.py \
  --outdir /tmp/exp_s3a \

# 2) Summarize it:

# 3) NPU latency:
python /home/ubuntu/rknn_model_zoo/examples/mms_tts/python/harness/bench_encoder.py --rknn <path.rknn> --runs 8

# 4) Full pipeline (fixed encoder + decoder, both .rknn = NPU):
python /home/ubuntu/rknn_model_zoo/examples/mms_tts/python/harness/run_pipeline.py \
  --encoder <fixed_encoder.rknn> --decoder ../model/mms_tts_eng_decoder_200.rknn \
  --out-wav /tmp/npu_fixed.wav --target rk3588

#    CPU/ONNX reference:
python /home/ubuntu/rknn_model_zoo/examples/mms_tts/python/harness/run_pipeline.py \
  --encoder ../model/mms_tts_eng_encoder_200.onnx --decoder ../model/mms_tts_eng_decoder_200.onnx \
  --out-wav /tmp/ref_cpu.wav --target rk3588   # target ignored for onnx
```

Key metrics to look for after each variant:
- `runtime/log_duration-rs.txt` — range must be non-constant and
  `max|rt-gold| < 0.1` to call a fix.
- `log_duration` shapes are **both flattened to (200,)** in the dumps; confirm
  `golden` and `runtime` snapshot sizes match before comparing (summarize.py
  does this and flags `SHAPE MISMATCH`).

## 6. Attempted hypothesis triage (the discipline that must be followed)

1. Every reported number must come from a command run in *this* session;
   paste command + raw output together. Anything not run = "NOT VERIFIED".
2. `op_target` keys must be **actual node names in this graph** (confirmed via
   graph dump), never op-type strings — op-type keys were never shown to map in
   this version's API.
3. Change exactly ONE variable per rebuild (one node to CPU, `do_quantization`,
   or `optimization_level`), then re-run `accuracy_analysis` and compare
   `runtime/log_duration-rs.txt` vs `golden/log_duration-rs.txt`.
4. Avoid trusting earlier, unverified claims (read `softplus_fix.md` only as a
   cautionary tale).

## 7. Known gotchas

- `accuracy_analysis` builds from the ONNX with **its own config**, so it does
  NOT reflect `convert.py`'s `op_target`. To test what `convert.py` produces,
  build with `convert.py` and check with `bench_encoder.py` (real NPU inference),
  not with `accuracy_analysis`.
- `rknn.config` uses `target_platform=`; a bare `target=` kwarg fails.
- If a variant's build warns or errors about an `op_target` key, that is
  useful info — a silently ignored key produces a false "no fix". Always run
  with `--verbose-log` when in doubt and grep for your node name and "cpu".
- Forced-to-CPU ops usually show up in the RKNN build log as
  `assign/can not assign ... second core` or similar lines; grep the verbose
  log for the exact node name.
